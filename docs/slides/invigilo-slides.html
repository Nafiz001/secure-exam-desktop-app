02 · Architecture

Three layers. One process tree.

Electron's main process owns the OS-level window, supervises the backend, and runs proctoring. The renderer is a pure UI shell — it never touches the database directly. Everything flows through the local REST API.

INVIGILO·ARCHITECTURE

03 · Exam Lifecycle

From room code to graded submission

Every exam follows the same five-step path. Server-side automation removes friction: students get a passwordless join, teachers get auto room codes, and MCQs grade themselves the moment the timer hits zero.

01

Create

Teacher defines exam type (lab_quiz/lab_test), duration, and adds MCQ / written / coding questions.

02

Join

Student enters name + roll + room code. Server auto-provisions an account and issues a JWT — no signup.

03

Start

Teacher flips status to in_progress. Window locks fullscreen, proctoring monitor activates.

04

Answer

MCQs · written text · Monaco editor for coding with live local execution against sample I/O.

05

Evaluate

MCQs auto-grade. Written & coding answers hit the Evaluation Desk for teacher review.

Auto magic: room codes exclude confusing chars (0/O/1/I/L), a background job syncs expired exams to completed, and submissions persist a violation log JSON for audit.

04 · Proctoring

Security at the OS layer, not the DOM

Because Invigilo is a native Electron window, proctoring runs in the main process — outside the renderer's reach. The student can't DevTools their way past it.

Window lockdown

During an active exam the window is forced fullscreen, always-on-top, and visible across workspaces.

  • Minimize / resize / close disabled
  • Fullscreen exit instantly reverted
  • Alt+F4 and F11 intercepted

Process scanner

ps-list runs every second, matching against a deny-list of cheating tools.

  • OBS Studio · Bandicam
  • AnyDesk · TeamViewer
  • Substring match — any rename attempt caught

Violation tracking

Every event is graded (low / medium / high), tallied, and surfaced to the teacher in real time.

  • Blur / focus loss → medium
  • Fullscreen exit → high
  • Threshold reached → auto-submit
OBSERV PATTERN  ·   Main process emits violation events over IPC; renderer subscribes via onViolation. Tampering with the UI cannot stop detection.

05 · Code Execution & Evaluation

A local judge — and a desk for the rest

Coding questions run on the student's own machine in a temp dir with bounded timeout. Written answers and edge-case code submissions land in the Evaluation Desk for the teacher to score and comment.

Local code judge · Strategy pattern

No external judge API. Per-request mkdtemp sandbox, child-process execution, timeouts enforced at 8s run / 12s compile.

JavaScript Python C C++
// backend/controllers/codeExecutionController.js const dir = await mkdtemp(`/tmp/invigilo-`); await writeFile(`${dir}/main.${ext}`, source); const child = exec(compileCmd, { cwd: dir, timeout: 12000 }); // run with sample I/O, capture stdout/stderr

Evaluation desk

Server auto-grades MCQs the instant a student submits. Everything else — written answers, edge-case code — opens here for teacher review with per-question marks and comments.

  • Per-participant submission picker
  • Side-by-side answer vs. reference answer
  • Auto-score + manual-score combined into total
  • Evaluation status: pending → completed
  • Violation JSON preserved on every submission
